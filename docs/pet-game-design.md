**도미네 강아지 게임 구현 설계**

SVG+HTML 렌더링을 유지하고, 먼저 개인 진행 시스템과 조작 반응을 완성한다. 이후 실사 사진을 스프라이트로 교체한다. 한 화면의 강아지 1마리, NPC 1명, 소품 몇 개를 표현하는 데 PixiJS를 추가할 실익은 작다.

목표는 **“돌보기 → 개인 보상 → 꾸미기 → 산책하며 발견하기”가 끊김 없이 이어지는 작은 공동체 게임**이다. 소리, 퀘스트, 출석 보상, 유료 재화, 거래, 개인 재산 순위는 넣지 않는다.

아래 성능·용량 수치는 구현의 합격 기준이며 실측 결과가 아니다. 검토 기준은 현재 작업 폴더의 코드다. 작업 폴더에 이미 있던 미커밋 변경도 포함되므로, 후속 구현자는 해당 변경을 덮어쓰지 않는다.

**현재 코드에서 유지할 것과 바꿀 것**

| 현재 구현 | 설계 결정 |
|---|---|
| `app/games/page.tsx`가 `/#home-pet`으로 이동 | 유지. 실제 게임 진입점은 `LandingPage.tsx`의 `PetGame`이다. |
| 도미·미네의 공동 수치와 성장 단계 | 유지. 개인 레벨과 강아지 성장 단계를 별개로 표시한다. |
| `domine_pet_state_for/care_for`와 구버전 RPC 대체 호출 | 유지. v6 기능을 별도로 추가한다. |
| v4·v5의 행동 쿨다운 0초 | 공동 돌봄 규칙은 유지하되, 개인 보상에는 별도 지급 간격을 둔다. |
| 수치가 가득 차면 돌봄 거절 | 개인 놀이와 진행은 허용한다. 공동 수치 적용 여부와 개인 보상 여부를 분리한다. |
| `PetGame`의 `sceneBusy`와 `PetScene`의 `running` | 하나의 reducer가 관리하는 상태 기계로 교체한다. |
| `PetScene.makePlan()`의 무작위 좌표 | 맵별 안전 영역 안에서 생성하는 순수 함수로 분리한다. |
| `preloadArt()`가 두 강아지·소품을 일괄 로드 | 현재 강아지·현재 맵·현재 행동만 로드한다. |
| 배경 로드와 `map` 변경이 분리됨 | 배경·NPC·장애물·표지판을 하나의 맵 묶음으로 전환한다. |
| `blip()`, `SOUND_KEY`, `sound` 상태 | 제거한다. |
| `bumpStreak()`와 연속 방문 표시 | 제거한다. 출석 압박을 만들지 않는다. |
| 현재 사진·자세 이미지 | 스프라이트 실패 시 사용할 대체 자산으로 보존한다. |

기존 서버의 수치 감소는 시간당 배부름 6, 기분 5, 청결 3이며, 성장 단계는 공동 돌봄 30회·100회 기준이다. 이 값은 이번 개인 진행 도입에서 바꾸지 않는다.

**기록의 소유권과 별명 보호**

| 항목 | 소유 범위 | 결정 이유 |
|---|---|---|
| 배부름·기분·청결·공동 돌봄 횟수 | 강아지별 공동 | 친구들이 함께 돌보는 성격을 유지한다. |
| 경험치·레벨·코인 | 별명별 개인 | 다른 사람의 접속 여부에 진행이 좌우되지 않게 한다. |
| 소지품·도감·업적 | 별명별 개인 | 구매와 발견의 결과를 자기 기록으로 남긴다. |
| 강아지 착장 | **보는 사람마다 자기 착장** | 공동 착장 덮어쓰기와 장난을 없앤다. |
| 장난감·개인 장식 | 보는 사람의 장면에만 표시 | 소유권과 화면 결과를 일치시킨다. |
| 성장 단계 | 강아지별 공동 | 개인 레벨을 올려도 강아지 크기를 독점하지 않는다. |
| GPS 장소 기념 | 해당 기기에만 보관 | 장소 방문 사실도 서버로 보내지 않는다. |

착장은 `(개인, 강아지)`별로 저장한다. 도미에게 입힌 옷이 미네에게 자동 적용되지 않지만, 구매한 옷은 두 강아지에게 모두 사용할 수 있다. 옷은 한 벌, 장난감은 한 개만 동시에 선택한다.

별명만으로 개인 재산을 수정하도록 두지 않는다. **별명 + 기기 비밀 토큰**을 사용한다.

- 별명: NFC 정규화, 앞뒤 공백 제거, 한글·영문·숫자 1~8자.
- 중복 판정: 영문 소문자로 비교한다. `Domi`와 `domi`는 같은 별명이다.
- 최초 시작: `crypto.getRandomValues()`로 32바이트 토큰을 생성한다.
- 전송 형식: 소문자 16진수 64자. HTTPS의 RPC POST 본문으로만 전달한다.
- 서버 저장: 토큰의 SHA-256 해시만 보관한다.
- 기기 저장: 별명별 토큰을 `localStorage`에 저장한다.
- 인증 실패: 기존 개인 기록을 덮어쓰거나 새 토큰으로 재등록하지 않는다.
- 기록 이전: 사용자가 직접 복사하는 `별명:토큰` 형식의 이전 코드를 제공한다. URL·QR 링크·분석 로그에 넣지 않는다.
- 저장소 사용 불가: 공동 돌봄·화면 놀이는 가능하지만 개인 기록 시작은 막고 이유를 표시한다.
- 토큰 분실: 별명만으로 복구하지 않는다. 새 별명으로 시작하거나 운영자가 별도로 확인해야 한다.

기존 `domine_pet_log`의 별명 기록은 소유자 증명이 없으므로 개인 경험치로 소급 환산하지 않는다. 첫 등록자가 실제 별명의 주인인지 확인할 수 없다는 한계도 남는다. 토큰은 **등록 이후의 덮어쓰기 방지책**이다.

기존 공개 RPC를 유지하므로 공동 수치와 과거 방식의 별명 표시는 여전히 장난에 취약하다. 새 개인 재산·배지는 기존 로그에서 계산하지 않아 영향을 차단한다.

**폰 세로 화면과 조작 반응**

기본 상태에서 게임 구역은 약 400px를 유지한다. 360~430px 폭에서는 다음 구성을 사용한다.

| 구역 | 높이 | 내용 |
|---|---:|---|
| 상단 | 44px | 도미/미네 선택, 별명·기록 관리 |
| 개인 진행 | 32px | `Lv. 7`, 경험치 막대, 코인 |
| 장면 | 약 180~220px | 기존 16:9 장면, 공동 수치 겹쳐 표시 |
| 행동 분류 | 44px | 먹이·돌봄·놀이 |
| 행동 버튼 | 44px | 선택 분류의 행동 |
| 하단 메뉴 | 44px | 상점·도감·업적 |
| 합계 | 약 388~428px | 바깥 여백 제외 |

320px 화면에서는 높이를 억지로 고정하지 않는다. 터치 영역 44px와 본문 가독성을 먼저 지킨다. 기록 목록은 기본 화면에서 빼고 기록 시트로 옮긴다.

상점·도감·업적은 동일한 시트 컴포넌트를 사용한다.

- 아래에서 220ms 동안 올라오는 전체 화면 `<dialog>`.
- 높이 `100dvh`, `100vh` 대체 선언, 하단 `safe-area-inset-bottom`.
- 제목·닫기 버튼 고정, 목록만 스크롤.
- 한 번에 하나의 시트만 연다. 상품 상세는 시트 내부 화면으로 전환한다.
- 뒤로 가기: 상세 → 목록 → 시트 닫기 순서.
- 닫기 후 열었던 버튼으로 포커스를 돌려준다.
- 열려 있는 동안 배경 스크롤과 장면 애니메이션을 정지한다.
- 도감은 3열, 24개씩 “더 보기”. 미발견 항목도 이름·조건을 공개한다.
- 미발견 항목에는 공통 실루엣을 사용하고 실제 이미지는 내려받지 않는다.

손맛은 다음 값으로 고정한다.

| 상황 | 화면 반응 | 진동 |
|---|---|---|
| 버튼 누름 | 즉시 `scale(0.96)`, 90ms 복귀 | 지원 기기에서 10ms |
| 개인 보상 확정 | 코인 최대 5개가 450ms 동안 코인 표시로 이동, `+N` 800ms | 15ms |
| 새 도감 | 작은 이미지와 이름을 1.2초 표시 | 20ms |
| 레벨 상승 | 장면 위 배너 1.4초, 입자 최대 12개 | `[15, 40, 20]` |
| 구매 성공 | 선택 물품 체크 표시 500ms | 15ms |
| 실패·보상 제한 | 버튼 옆 한 줄 안내 | 없음 |

코인 효과는 서버의 지급 확정 뒤에만 실행한다. 버튼 누름 자체의 반응은 통신을 기다리지 않는다.

진동은 지원 여부와 기기 설정에 따라 동작하지 않을 수 있으므로 모든 정보를 화면으로도 전달한다. `prefers-reduced-motion`에서는 이동 입자와 확대 연출을 없애고 숫자·체크 표시로 대체하며, 진동 기본값도 끈다. [MDN Vibration API](https://developer.mozilla.org/en-US/docs/Web/API/Navigator/vibrate)

**렌더링·로딩·성능 예산**

렌더러는 **기존 SVG+HTML 유지**로 결정한다. 외부 게임 엔진의 추가 번들은 0KB다. 스프라이트 재생은 작은 SVG 이미지 창과 프레임 인덱스로 구현한다.

이 장면에서 병목 가능성이 큰 부분은 엔진 부재보다 일괄 이미지 로드, 중복 타이머, 필터, React 상태 갱신이다. 먼저 이를 제거한다.

| 항목 | 합격 기준 |
|---|---:|
| 기존 사이트 대비 첫 화면 추가 JS | gzip 45KB 이하 |
| 위 예산 중 스프라이트 재생 코드 | gzip 8KB 이하 |
| 시트 3종의 지연 로드 JS 합계 | gzip 25KB 이하 |
| 게임 첫 표시 이미지 총량 | 240KB 이하 |
| 현재 대비 첫 표시 이미지 증가량 | 150KB 이하 |
| 행동 이미지 추가 전송 | 처음 실행하는 행동당 100KB 이하 |
| 도감·상점 첫 목록 이미지 | 120KB 이하 |
| 게임의 추가 JS 힙 | 20MB 이하 |
| 동시에 참조하는 디코딩 이미지 | 계산상 24MiB 이하 |
| 게임 장면 DOM/SVG 노드 | 250개 이하 |
| 움직임 목표 | 60fps, 저사양 기기에서 지속 30fps 이상 |
| 프레임 시간 | 동작 중 p95 33.3ms 이하 |
| 누름 후 시각 반응 | 100ms 이내 |
| 장면 전환 누적 레이아웃 이동 | 0 |
| 게임 구역 이탈·탭 비활성 시 | 프레임 루프·폴링 정지 |

스프라이트 자체는 걷기 12fps, 나머지 6~8fps로 재생한다. 위치 이동은 브라우저의 transform 보간을 사용하므로 스프라이트 fps와 화면 fps는 별개다.

`PetGame.tsx`는 클라이언트 컴포넌트로 유지한다. 시트는 이 파일에서 `next/dynamic`으로 선언하고, 열 때만 렌더한다. GPS 모듈도 버튼을 누른 뒤 `import()`한다. 브라우저 전용 코드에 `ssr: false`가 필요하면 반드시 클라이언트 경계 안에서 지정한다. 이는 설치된 Next.js 16.2.1의 `node_modules/next/dist/docs/01-app/02-guides/lazy-loading.md` 기준이다.

이미지 로더는 다음 정책으로 바꾼다.

1. 최초: 현재 맵 배경 1장, 현재 강아지 기본 자세, 필요한 NPC만 로드.
2. 행동 선택: 해당 행동 자산만 로드.
3. 인접 맵: 사용자가 이동 버튼을 누를 때 로드.
4. 최근 사용한 행동 atlas 최대 4개, 배경 최대 2개를 메모리 참조에 유지.
5. 화면 밖 도감 이미지에는 `loading="lazy"`.
6. SVG 내부 이미지는 최적화한 WebP를 직접 참조한다.
7. 첫 화면 이후에도 전체 자산 일괄 preload는 하지 않는다.

`visibilitychange`, `pagehide`, 게임 구역의 `IntersectionObserver`를 사용한다. 탭이 숨겨지면 자동 반복 애니메이션과 폴링을 멈추고, 복귀 시 상태를 한 번 동기화한다. 브라우저 자체의 타이머 지연에만 의존하지 않는다. [MDN Page Visibility API](https://developer.mozilla.org/en-US/docs/Web/API/Page_Visibility_API)

저사양 모드는 최근 2초의 프레임 시간이 지속적으로 예산을 넘으면 켠다. 입자 수를 3개로 줄이고, 대기 애니메이션을 정지하며, 스프라이트를 6fps로 낮춘다. 사용자의 게임 진행이나 발견 확률은 바꾸지 않는다.

**잠금·타이머·맵 전환을 관리하는 상태 기계**

현재 코드에서 잠금의 정확한 재현 원인은 확정하지 않았다. 다만 `busy`, `sceneBusy`, `running`, 부모의 30초 안전 타이머, 자식의 여러 종료 타이머가 독립적으로 존재한다. `sleep`은 중간 단계와 최종 단계에서 완료 신호를 보낼 수 있다. 이 구조를 제거한다.

하나의 reducer 안에서 화면 연출과 서버 요청을 분리해 관리한다.

```ts
type VisualPhase =
  | "idle"
  | "acting"
  | "loading-map"
  | "switching-map"
  | "sleeping"
  | "paused";

type CommandPhase =
  | "idle"
  | "pending"
  | "uncertain";

type GameMachine = {
  visual: VisualPhase;
  command: CommandPhase;
  epoch: number;
  sceneId: number;
  operationId: string | null;
  startedAt: number | null;
  deadlineAt: number | null;
  committedMap: PetMap;
  pendingMap: PetMap | null;
};
```

| 현재 상태·사건 | 다음 상태와 처리 |
|---|---|
| `idle` + 행동 누름 | 누름 반응 즉시 표시, 요청은 `pending`, 연출 준비 |
| RPC 성공 | 확정 보상을 반영하고 해당 연출 실행 |
| 공동 수치 적용 거절·개인 보상 성공 | 놀이 연출과 개인 보상 표시 |
| 통신 8초 초과 | `uncertain`, 연출 잠금 해제, “결과 확인” 버튼 활성화 |
| 연출 완료 | 일치하는 `sceneId`일 때만 `idle` |
| 연출 마감 초과 | 마지막 안전 자세로 이동하고 `idle` |
| 재우기 완료 | `sleeping`; 다음 행동을 누르면 즉시 깨움 |
| 맵 이동 | `loading-map` → 준비 완료 → `switching-map` → `idle` |
| 이미지 실패·4초 초과 | 준비된 단색/SVG 대체 배경으로 전환 |
| 숨김·언마운트 | epoch 무효화, 구독·타이머·RAF·이미지 콜백 취소 |
| 복귀 | 오래된 연출은 끝낸 것으로 처리, 서버 상태 재조회 |

`sceneBusy`라는 별도 state/ref는 없앤다. 입력 제한은 현재 상태에서 계산한다. 시트 닫기, 기록 보기, 통신 재확인은 연출 때문에 잠그지 않는다.

서버 결과가 불확실한 경우 새 경제 요청을 만들어 재시도하지 않는다. 동일한 `operationId`와 동일한 명령을 재전송한다. 확인 전에도 로컬 쓰다듬기·맵 보기·도감 열기는 가능하다.

연출은 다음 구조로 바꾼다.

```ts
type ScenePlan = {
  durationMs: number;
  keyframes: readonly SceneKeyframe[];
  finalPose: ScenePose;
};

function buildScenePlan(
  action: SceneAction,
  context: SceneContext,
  random: () => number
): ScenePlan;

function sampleScenePlan(
  plan: ScenePlan,
  elapsedMs: number
): ScenePose;

function gameReducer(
  state: GameMachine,
  event: GameEvent
): GameMachine;
```

- 행동 연출은 최대 4.5초, 종료 유예는 500ms.
- 단일 스케줄러가 현재 경과시간으로 장면을 계산한다.
- 단계마다 `setTimeout`을 생성하지 않는다.
- 말풍선은 별도 표시 상태이되 버튼 잠금을 소유하지 않는다.
- 완료 이벤트는 `sceneId`로 한 번만 처리한다.
- 비동기 완료 직후에는 항상 `epoch`, 별명, 강아지 ID를 확인한다.
- cleanup 이후 `await`가 끝나도 새 타이머를 만들 수 없게 한다.
- RPC 취소는 서버 트랜잭션 취소를 보장하지 않으므로 중복 방지는 서버 요청 ID가 담당한다.

맵 전환은 `committedMap`을 렌더링 기준으로 사용한다. `pendingMap`의 배경 `decode()`와 필수 자산 준비가 끝나면 배경·장애물·NPC·클릭 영역을 **같은 상태 변경에서** 교체한다. 전환 180ms 동안 입력을 잠깐 막는다. 강아지가 화면 밖으로 나갔다가 돌아오는 현재 맵 이동 연출은 제거한다.

**공놀이와 맵별 안전 영역**

논리 좌표는 현재 `viewBox="0 6 160 90"`을 유지한다. 모든 좌표는 CSS 픽셀이 아닌 이 논리 좌표를 따른다.

이동 판단은 강아지 중심점이 아니라 **자세·꼬리·착장·들고 있는 물체를 포함한 외곽**을 사용한다. 공은 별도 반지름을 가진다.

아래 값은 새 배치의 기준이다. NPC와 개집도 이 배치에 맞춰 옮긴다.

| 맵 | 강아지 발 기준 이동 영역 `(x1,x2,y1,y2)` | 장애물 배치 | 시작점 |
|---|---|---|---|
| 성당 마당 | `(46,140,77,84)` | 신부님 `(8,31)-(25,74)` | `(85,82)` |
| 들판 | `(20,140,76,84)` | 이동 영역 안에 고정 장애물 없음 | `(80,82)` |
| 당정동 | `(20,140,77,84)` | 가게 영역 `y≤65`, 차량 표현 없음 | `(80,82)` |
| 공원 숲길 | `(22,138,77,84)` | 나무·벤치는 이동 영역 바깥 배경 | `(80,82)` |
| 집 마당 | `(22,98,78,84)` | 개집 `(120,48)-(156,84)` | `(66,82)` |

성견의 장면상 몸통 폭은 기본 26, 어린 강아지 22, 아기 18로 맞춘다. 미네는 여기에 0.72배를 적용한다. 성당은 추가 0.85배다. 외곽 판정은 수치 폭이 아닌 실제 프레임의 합집합 경계를 사용한다.

```ts
function actorBounds(
  pose: ScenePose,
  sprite: SpriteMeta,
  equipment: EquipmentMeta | null
): Rect;

function clampActor(
  desiredFoot: Point,
  bounds: RelativeBounds,
  zone: SafeZone
): Point;

function buildBallPath(
  from: Point,
  to: Point,
  radius: number,
  zone: SafeZone
): QuadraticPath;
```

공놀이는 다음 규칙으로 단순화한다.

- 던질 목표는 안전 영역 안에서 선택한다.
- 공 중심의 허용 영역은 화면 경계에서 반지름+3만큼 줄인다.
- 포물선 최고점은 `y≥18`.
- 바닥 공 중심은 `y≤84`.
- 강아지가 공을 물었을 때의 합성 외곽도 검사한다.
- 튕김과 굴림의 끝점에도 같은 검사를 적용한다.
- 임의 좌표를 만든 뒤 일부 단계만 clamp하지 않는다. **모든 keyframe과 보간 경로를 검증**한다.
- 안전한 경로를 만들 수 없으면 제자리 공놀이로 바꾼다.
- 화면 clipping은 최종 방어선일 뿐 위치 계산의 대체물이 아니다.

신부님은 성당 마당에만 등장한다. 개집 문으로 들어가는 재우기는 전용 경로로 처리하고, 일반 놀이의 안전 영역에는 개집을 포함하지 않는다.

**개인 경험치·코인·레벨**

공동 돌봄 성공 여부와 개인 보상 지급 여부를 각각 반환한다.

예를 들어 배부름이 100이어도 밥주기는 그릇을 정리하는 짧은 연출을 보여 주고 개인 보상을 받을 수 있다. 서버가 공동 수치를 올렸다고 거짓 표시하지 않도록 `공동 수치는 충분해요 · 함께한 보상 +4`처럼 안내한다.

| 행동 | XP | 코인 | 개인 보상 간격 | 연출 목표 |
|---|---:|---:|---:|---:|
| 밥주기 `feed` | 8 | 4 | 같은 행동 60초 | 2.4초 |
| 간식 `treat` | 6 | 3 | 60초 | 2.2초 |
| 쓰다듬기 `pet` | 5 | 2 | 60초 | 1.8초 |
| 공놀이 `play` | 10 | 5 | 60초 | 3.5초 |
| 산책 `walk` | 10 | 6 | 60초 | 4초 |
| 빗질 `brush` | 8 | 4 | 60초 | 2.6초 |
| 목욕 `bath` | 10 | 5 | 60초 | 3.2초 |
| 훈련 `train` | 10 | 5 | 60초 | 3초 |
| 재우기·강아지 직접 탭·NPC 인사 | 0 | 0 | 로컬 연출만 | 0.5~2초 |
| 유효 탐색 완료 | 4 | 2 | 탐색 규칙 적용 | 결과 표시 |
| 도감 중복 발견 | 0 | 추가 1 | 보상 가능한 탐색에서만 | 중복 표시 |
| GPS 200m 보상 | 8 | 4 | 최소 150초, 하루 4회 | 결과 표시 |

개인 보상 규칙은 두 강아지를 합산한다.

- 보상 행동 사이 최소 10초.
- 같은 행동 보상은 60초에 한 번.
- 하루 보상 행동 최대 40회.
- 한도 이후에도 로컬 놀이 가능.
- 서버 상태를 바꾸는 돌봄 요청은 개인당 10초에 한 번까지.
- 공동 돌봄은 기존 전체 20회/분 제한을 그대로 따른다.
- 공동 제한에 걸려도 개인 보상 자격은 별도로 판단한다.
- 하루는 서버의 `Asia/Seoul` 날짜 기준.
- 재우기·새로고침·별명 화면 열기에 보상을 주지 않는다.
- 업적은 배지만 지급하고 재화는 지급하지 않는다.
- 도감 최초 발견 자체에는 추가 XP를 주지 않는다. 탐색 보상과 중복 계산을 줄인다.

레벨은 1~30이다.

```text
레벨 L 진입 누적 XP = 10 × (L−1) × (L+2)
L → L+1 필요 XP = 20L + 20
레벨 상승 코인 = 10 + 2 × 도달 레벨
```

| 레벨 | 누적 XP | 레벨 | 누적 XP | 레벨 | 누적 XP |
|---:|---:|---:|---:|---:|---:|
| 1 | 0 | 11 | 1,300 | 21 | 4,600 |
| 2 | 40 | 12 | 1,540 | 22 | 5,040 |
| 3 | 100 | 13 | 1,800 | 23 | 5,500 |
| 4 | 180 | 14 | 2,080 | 24 | 5,980 |
| 5 | 280 | 15 | 2,380 | 25 | 6,480 |
| 6 | 400 | 16 | 2,700 | 26 | 7,000 |
| 7 | 540 | 17 | 3,040 | 27 | 7,540 |
| 8 | 700 | 18 | 3,400 | 28 | 8,100 |
| 9 | 880 | 19 | 3,780 | 29 | 8,680 |
| 10 | 1,080 | 20 | 4,180 | 30 | 9,280 |

레벨 30에서는 XP 표시를 9,280으로 고정하지만 코인·도감·업적 진행은 계속된다. 레벨 상승 보상은 하나의 트랜잭션에서 넘은 레벨 모두를 계산한다.

하루 행동 10회와 탐색 6회면 대략 XP 100, 코인 50~60을 얻는다. 첫 40코인 상품은 첫 긴 방문 또는 두 번째 방문에 살 수 있고, 레벨 30은 이 이용량에서 약 3개월 목표다. 레벨에 따라 발견 확률이나 공동 돌봄 능력을 올리지 않는다.

**상점과 착용**

상점은 정가 구매만 제공한다. 뽑기, 판매, 환불, 선물, 거래는 없다. 같은 상품은 한 번만 구매할 수 있으며, 수량은 1이다.

옷은 `wearable` 슬롯 하나로 통일한다. 모자와 옷을 동시에 겹치는 기능은 만들지 않는다. 장난감은 `toy` 슬롯 하나다. 장난감을 선택하면 장면의 지정 위치에 나타나고 공놀이 시 해당 물체를 사용한다.

모든 상품은 레벨 1부터 구매할 수 있다. 레벨 제한을 추가해 코인을 갖고도 사지 못하는 상황을 만들지 않는다.

아래 도감의 061~080번이 상점 가격표이자 소지품 목록이다. 전례색 기본 목줄은 무료 기본 표현이며 판매하지 않는다. 성직자 복장·제의·성물은 강아지 의상이나 장난감으로 만들지 않는다.

**도감 96종**

도감은 **상시 완성 80종 + 전례 시기 기록 12종 + 기기 전용 산책 기념 4종**으로 나눈다. 기본 진행률과 업적은 상시 80종만 사용한다. 시기를 놓치거나 GPS를 거절해도 기본 도감을 완성할 수 있다.

희귀도는 `일반·특별·희귀·아주 드묾`이며 등장 빈도만 뜻한다. 전례·신앙 소재에는 희귀도 대신 `기념`을 사용한다.

표의 이미지 확보 방식은 다음과 같다.

- **G**: Codex 생성 4×4 물건 시트 → 개별 투명 WebP.
- **N**: Codex 생성 3×2 인물·동물 시트 → 개별 WebP.
- **B**: Codex 생성 장소 삽화 시트 → 개별 WebP. 실제 장소의 정확한 재현이라고 표시하지 않는다.
- **W**: Codex 생성 착용품 시트 → 아이콘과 장면용 레이어 공용.
- **L**: Codex 생성 전례 기록 삽화 → 설명 검수 후 사용.
- **P**: Codex 생성 산책 기념 그림 → 기기에서만 사용.

외부 무료 이미지·아이콘은 이번 자산 계획에 포함하지 않는다. 따라서 불명확한 “무료 이미지”를 가져오는 단계도 없다. 기존 사진을 참조하는 경우 저장소에서 이미 사용하는 자산만 사용한다.

`발견`은 해당 맵의 유효 탐색 완료 시 추첨한다는 뜻이다. 별도 표기가 없는 항목은 연중·모든 시간대에 등장한다.

**탐색과 등장 확률**

맵 이동이나 산책을 시작하면 서버가 탐색 티켓을 발급한다. 보상 계산은 연출 종료 콜백이 아닌 티켓 완료 RPC가 담당한다.

- 티켓은 개인당 하나만 활성화.
- 발급 간격 30초, 하루 최대 60회.
- 발급 후 15초부터 완료 가능, 10분 뒤 만료.
- 코인·XP·도감 추첨이 있는 완료는 하루 최대 30회.
- 화면을 바꿔도 산책 버튼을 계속 누를 필요는 없다.
- 15초가 지나면 같은 맵에 머무는 동안 자동으로 한 번 완료 요청.
- 다른 맵으로 이동하면 이전 티켓을 취소한다. 새 티켓 발급 제한은 초기화하지 않는다.
- 단순 새로고침·최초 진입에는 티켓을 발급하지 않는다.
- 서버는 가상 맵 ID와 티켓 시간만 검증한다. 실제로 화면을 봤는지는 증명하지 않는다.
- 시간대·전례 시기는 완료 시점의 서버 시간으로 판정한다.

| 맵 | 일반 후보 | 특별 후보 | 희귀 후보 | 아주 드문 후보 |
|---|---|---|---|---|
| 성당 | 001~006 | 007~009 | 010~011 | 012 |
| 들판 | 013~018 | 019~021 | 022~023 | 024 |
| 당정동 | 025~030 | 031~033 | 034~035 | 036 |
| 공원 | 037~042 | 043~045 | 046~047 | 048 |

시간대는 현재 배경 구분과 맞춘다.

| 시간대 | 한국 시간 | 적용 |
|---|---|---|
| 새벽 | 05:00~06:59 | 표에서 새벽으로 지정한 항목 |
| 낮 | 07:00~16:59 | 낮 항목 |

추첨은 다음 순서로 고정한다.

1. 75%로 발견, 25%로 발견 없음.
2. 발견 시 희귀도 추첨.
3. 해당 맵·시간대·시기 조건에 맞는 같은 희귀도 항목 중 균등 추첨.
4. 해당 희귀도 후보가 없으면 일반 후보로 이동한다.

| 희귀도 | 발견 성공 안에서 확률 | 탐색 1회 기준 기본 확률 |
|---|---:|---:|

| 특별 | 25% | 18.75% |
| 희귀 | 8% | 6% |
| 아주 드묾 | 2% | 1.5% |
| 발견 없음 | — | 25% |

위 기본 확률은 해당 시간대에 각 희귀도 후보가 존재하고, 아래 미발견 보정이 작동하지 않을 때의 값이다.

**미발견 보정:** 현재 맵·시간대에 미발견 후보가 있는데도 새 항목을 얻지 못한 탐색이 4회 연속이면, 다섯 번째에는 미발견 후보 하나를 보장한다. 희귀도 가중치는 65:25:8:2를 유지하고, 미발견 후보가 있는 희귀도끼리만 정규화한다.

보정 카운터는 개인별로 저장하고, 시간 조건상 후보가 없었던 탐색은 증가시키지 않는다. 보정으로 새 항목을 얻거나 일반 추첨에서 새 항목을 얻으면 0으로 초기화한다. 도감에 확률과 보정 규칙을 설명한다.

무작위 결과는 최초 완료 트랜잭션에서 저장한다. 응답 유실 후 재시도해도 다시 추첨하지 않는다.

**DB 스키마와 v6 마이그레이션**

새 SQL 파일은 **`supabase/migrations/20261111180000_domine_pet_v6.sql` 하나**로 한다. v5까지의 테이블과 함수를 전제로 하며, 적용 전 존재 여부를 검사한다. 전제가 맞지 않으면 전체를 중단한다.

기존 함수의 시그니처·본문·권한은 수정하지 않는다. 새 개인 테이블과 보조 함수는 비공개 스키마 `domine_pet_v6`에 둔다. 외부 진입 RPC만 `public`에 둔다.

**트랜잭션 순서**

행동 RPC는 다음 순서를 따른다.

1. 형식 검증.
2. 기존 v5와 같은 전역 advisory lock `(20261111,120000)` 획득.
3. 개인 행 `FOR UPDATE`, 토큰 검증.
4. 동일 요청 ID 조회. 있으면 입력 해시를 비교하고 기존 결과 반환.
5. 개인 제출 제한·일일 한도 판정.
6. 기존 `domine_pet_care_for()` 호출.
7. 공동 적용 결과와 독립적으로 개인 보상 자격 계산.
8. XP·코인·카운터·레벨 보상·배지 갱신.
9. 최종 응답을 `operation`에 기록.
10. 트랜잭션 종료.

구매·착용·탐색은 개인 행 잠금만 필요하다. 두 구매가 동시에 들어와도 같은 개인 행에서 직렬화되므로 잔액을 이중 소비하지 않는다.

구매는 서버 가격을 조회하고 잔액 확인, 코인 차감, 소지품 등록, 도감 등록, 업적 판정, 결과 저장을 한 트랜잭션으로 처리한다.

탐색 완료는 개인 행 다음에 티켓 행을 잠근다. 서로 다른 요청 ID로 같은 티켓을 두 번 완료해도 저장된 티켓 결과를 반환하며 추가 지급하지 않는다.

**RLS·권한·입력 검증**

- 새 스키마는 Supabase Data API 노출 스키마에 추가하지 않는다.
- 새 테이블 모두 RLS를 활성화하고 anon/authenticated 정책은 만들지 않는다.
- 스키마·테이블·시퀀스의 직접 권한을 `PUBLIC`, `anon`, `authenticated`에서 제거한다.
- 공개 진입 함수만 `security definer set search_path=''`.
- 모든 테이블·내부 함수·확장 함수는 스키마를 명시한다.
- 보조 함수의 `EXECUTE`는 `PUBLIC`, `anon`, `authenticated`에서 회수한다.
- 공개 RPC도 기본 `PUBLIC EXECUTE`를 먼저 회수한 뒤 필요한 역할에만 부여한다.
- 동적 SQL은 사용하지 않는다.
- `p_pet`, 행동, 맵, 슬롯, 항목 ID, UUID, 비밀 토큰 길이와 NULL을 명시적으로 검사한다.
- 토큰 해시는 `extensions.digest()` 등 실제 pgcrypto 설치 스키마를 명시한다.
- 클라이언트에 서비스 역할 키를 넣지 않는다.
- 토큰·요청 본문을 애플리케이션 로그나 오류 수집 도구에 남기지 않는다.

빈 `search_path`와 명시적 스키마 사용은 Supabase의 보안 함수 지침을 따른다. [Supabase Database Functions](https://supabase.com/docs/guides/database/functions)

도배 한도는 다음과 같다.

| 범위 | 한도 |
|---|---:|
| 개인의 새 변경 요청 | 30회/분 |
| 전체 v6 새 변경 요청 | 300회/분 |
| 개인 상태 조회 | 12회/분 |
| 신규 별명 등록 | 전체 10회/시간, 50회/일 |
| 같은 개인의 공동 돌봄 제출 | 10초에 1회 |
| 기존 공동 돌봄 성공 | 기존 전체 20회/분 유지 |

요청 ID 재조회는 지급 한도와 별개지만 조회 빈도 제한은 받는다. 신규 별명 제한은 첫 모임 사용량을 고려한 값이다. 한도 때문에 전체 가입이 막히면 운영자가 서버에서 조정한다.

이 구조는 IP 기반 공격 방어나 다중 별명 생성 방지가 아니다. anon 직접 RPC와 로그인 없는 조건에서 가능한 완화다. 코인 거래와 공개 개인 순위를 없애 악용 유인을 줄인다.

**SQL 적용 전 호환성**

1. 새 클라이언트는 `domine_pet_capabilities_v6()`를 호출한다.
2. 정확히 `PGRST202`이면 기존 `petRequest()`로 돌아간다.
3. v6가 없을 때는 진행 메뉴에 “준비 중”을 표시하고 기존 돌봄을 제공한다.
4. 네트워크 실패·인증 실패·서버 내부 오류를 “v6 없음”으로 처리하지 않는다.
5. v6 기능이 확인된 뒤 발생한 변경 오류를 기존 RPC로 재전송하지 않는다.
6. SQL은 `BEGIN`부터 `COMMIT`까지 한 번에 적용하고 마지막에 스키마 캐시를 갱신한다.
7. 기존 클라이언트는 SQL 적용 후에도 기존 RPC를 그대로 사용한다.

**Codex 이미지 생성과 스프라이트 제작**

그림은 **부드러운 2D 손그림풍, 둥근 실루엣, 얕은 명암, 과장하지 않은 표정**으로 통일한다. 실사와 픽셀아트를 섞지 않는다.

도미는 황금빛 골든 리트리버, 미네는 작은 흰 말티즈다. 신부님은 기존 자산을 참고한 차분한 검은 성직자 일상복과 로만 칼라로 표현한다. 전례 집전 장면이나 우스꽝스러운 과장은 만들지 않는다.

생성 순서는 고정한다.

1. 현재 사진을 참조해 세 캐릭터의 기준 모습을 만든다.
2. 도미·미네의 오른쪽 측면과 약한 3/4 측면 중 **오른쪽 측면 하나**를 기준으로 확정한다.
3. 확정 이미지를 매 생성 요청에 참조 이미지로 첨부한다.
4. 한 시트에는 한 캐릭터의 한 행동만 넣는다.
5. 다음 행동을 만들 때 이전 행동의 결과만 참조하지 않고 원래 기준 이미지를 함께 사용한다.
6. 실패한 행동만 다시 생성한다.
7. 연속 프레임의 모양 차이는 허용하되 크기·발 위치·몸 방향은 후처리로 고정한다.

프롬프트 공통 부분은 다음과 같이 사용한다.

```text
첨부된 기준 이미지의 동일한 캐릭터를 사용한다.
캐릭터의 머리 크기, 주둥이 길이, 귀 모양, 털색, 몸통 비율,
선 두께와 명암 단계를 유지한다.

오른쪽을 보는 고정 측면 카메라. 원근 변화, 카메라 이동, 확대 금지.
3열 2행, 정확히 같은 크기의 6칸.
왼쪽 위부터 오른쪽으로 시간 순서의 애니메이션 프레임.

격자선, 숫자, 글자, 그림자, 소품, 의상은 그리지 않는다.

```

행동별로 마지막 부분만 바꾼다.

```text
걷기: 제자리 걷기 6프레임. 몸의 이동 없이 다리의 보행 주기만 변화.
먹기: 바닥의 그릇을 향해 고개를 낮추고 씹은 뒤 돌아오는 6프레임.

꼬리 흔들기: 몸통과 발은 고정하고 꼬리와 표정만 작게 변화.
자기: 몸을 웅크린 수면 자세의 아주 작은 호흡 6프레임.
털기: 발 위치를 유지하며 몸과 털이 좌우로 움직이는 6프레임.
대기: 고정된 발 위치, 작은 호흡과 한 번의 눈 깜박임.
```

| 도미 | 대기·걷기·앉기·먹기·꼬리·자기·털기, 7장 | 3×2, 원본 목표 1536×1024, 칸 512×512 | 6~12fps |
| 미네 | 동일 7장 | 동일 | 동일 |
| 신부님 | 대기·손인사·걷기, 3장 | 동일 | 6~8fps |
| 도감 물건 | 16개씩 | 4×4, 원본 1024×1024 이상 | 정지 |
| 사람·동물 도감 | 6개씩 | 3×2 | 정지 |

브라우저용 강아지 프레임은 256×256이다. 잘라낸 프레임을 3×2의 768×512 atlas로 다시 합친다. atlas 한 장의 디코딩 크기는 약 1.5MiB다.

압축 목표는 행동 atlas 50~90KB, 정지 NPC 12~20KB, 물건 아이콘 3~6KB다. 한 행동 atlas가 100KB를 넘으면 품질을 낮추기 전에 프레임을 4개로 줄인다.

**`scripts/cut_sheet.py` 확장**

현재 스크립트는 연결 성분의 중심으로 칸을 추정하고, 물체마다 다른 크기로 잘라낸다. 물건 아이콘에는 쓸 수 있지만 애니메이션에는 위치 흔들림이 생긴다.

기존 기본 모드는 유지하고 다음 옵션을 추가한다.

```text
--mode item|sprite
--cell-width 512
--cell-height 512
--frame-size 256
--pivot 0.5,0.88
--keep-canvas
--strict-grid
--output-format png|webp
--manifest <경로>
```

sprite 모드의 처리 순서는 다음과 같다.

1. 시트 치수가 행·열 규격과 맞는지 확인한다.
2. **격자를 먼저 자른 뒤** 각 칸 내부에서 배경을 제거한다.
3. 기존 알파 채널이 있으면 우선 사용한다.
4. 단색 배경 제거는 각 칸의 외곽과 연결된 배경 영역을 기준으로 한다.
5. 발 기준점과 동일 캔버스를 유지한다. 프레임별 자동 확대는 금지한다.
6. 작은 흰 털이나 꼬리가 연결 성분 면적 기준으로 탈락하지 않게 한다.
7. 검정·흰색·회색 배경 위 미리보기를 만들어 번짐을 확인한다.
8. 빠진 프레임, 칸 경계 접촉, 프레임 수 불일치는 실패로 종료한다.
9. PNG 중간 결과는 `public/` 밖에 둔다.
10. `optimize_images.py`로 각 프레임을 최적화하고, 최적화 프레임을 atlas로 묶는다.
11. 최종 atlas도 `optimize_images.py --kind character --width 768`을 통과시킨다.

`--width 768`은 전체 atlas를 대상으로 한 명시적 예외다. 각 캐릭터 프레임은 256px로 이미 축소되어 있다. 전체 atlas에 기본 640px 축소를 적용해 프레임 경계를 깨뜨리지 않는다.

manifest에는 다음 정보를 기록한다.

```ts
type SpriteFrame = {
  rect: { x: number; y: number; w: number; h: number };
  pivot: { x: number; y: number };
  bounds: { left: number; top: number; right: number; bottom: number };
  anchors: {
    neck: Point;
    body: Point;
    head: Point;
    mouth: Point;
  };
};

type SpriteClip = {
  src: string;
  fps: number;
  loop: boolean;
  frames: readonly SpriteFrame[];
};
```

옷은 이 anchor에 맞춰 크기·회전을 적용한다. 좌우 반전은 강아지와 착장에 같은 부모 transform을 적용한다. 몸통 옷이 크게 어긋나는 자세는 프레임별 보정값을 manifest에 넣는다.

실패 판정은 다음과 같다.

- 행동별 재생성은 최대 2회.
- 발 기준선 오차가 출력 기준 3px를 넘으면 후처리 보정.
- 같은 행동의 머리·몸 크기 차이가 약 10%를 넘으면 재생성.
- 다리 추가·얼굴 붕괴·칸 침범이 남으면 해당 행동만 기존 사진+CSS 연출로 대체.
- 스프라이트 로딩 실패도 동일한 사진 대체 경로를 사용.
- 캐릭터 전체를 한 번에 실패 처리하지 않는다.

**GPS 선택 기능**

GPS는 “실제 산책을 조금 더 기념하는 기능”이다. 켜지 않아도 레벨 30, 상점 전체, 상시 도감 80종, 업적 30개를 모두 달성할 수 있다.

Geolocation은 HTTPS와 명시적 사용자 권한이 필요하다. 앱 설치나 PWA 설치는 요구하지 않는다. [MDN watchPosition](https://developer.mozilla.org/en-US/docs/Web/API/Geolocation/watchPosition)

권한 흐름은 다음과 같다.

1. 놀이 시트에서 “실제 산책” 선택.
2. “화면이 켜진 동안만 측정하며, 좌표는 전송하지 않습니다” 표시.
3. 사용자가 “위치 사용하고 시작”을 눌렀을 때만 권한 요청.
4. 허용되면 위치 측정을 시작하고 서버 산책 세션 발급.
5. 거부되면 “화면 속 산책 계속하기”로 돌아간다.
6. 자동 재요청하지 않는다.
7. 중지·탭 숨김·화면 잠금·페이지 이탈 시 `clearWatch()`를 호출한다.
8. 복귀 시 이전 위치와 새 위치를 연결하지 않는다.

화면이 꺼진 동안의 거리나 걸음 수를 측정한다고 표시하지 않는다. 브라우저 Geolocation만으로 실제 걸음 수를 알 수 없으므로 UI는 “걸음 수” 대신 “산책 거리”를 사용한다.

위치 요청 설정은 다음으로 시작한다.

```ts
{
  enableHighAccuracy: true,
  maximumAge: 5000,
  timeout: 15000
}
```

기기 내부 거리 계산 규칙은 다음과 같다.

| 조건 | 처리 |
|---|---|
| 최초 위치 | 기준점만 설정, 거리 0 |
| 정확도 `accuracy>30m` | 거리 계산 제외, “위치가 불안정해요” |
| 위치 시각이 현재보다 10초 이상 오래됨 | 제외 |
| 시간 역전·중복 timestamp | 제외 |
| 샘플 간격 3초 미만 | 계산 생략 |
| 샘플 간격 30초 초과 | 기준점 재설정, 구간 거리 0 |
| `coords.speed>3m/s` | 차량 의심, 해당 구간 제외 |
| 두 점 거리/시간 `>3m/s` | 동일 처리 |
| 이동량 `<max(8m, 0.5×(양끝 정확도 합))` | 정지 흔들림으로 보고 누적하지 않음 |
| 유효 이동 | Haversine 거리에서 `0.25×(양끝 정확도 합)`을 뺀 보수적 거리 누적 |
| 차량 의심 이후 | 유효 저속 위치 3개를 확인한 뒤 새 기준점부터 재개 |

Haversine 계산의 지구 반지름은 6,371,000m를 사용한다. 정지 흔들림을 줄이는 대신 거리를 다소 적게 계산하는 쪽을 선택한다.

```ts
type GeoSample = {
  latitude: number;
  longitude: number;
  accuracy: number;
  speed: number | null;
  timestamp: number;
};

function acceptGeoSample(
  state: LocalWalkState,
  sample: GeoSample
): {
  state: LocalWalkState;
  acceptedMeters: number;
  reason: string;
};
```

좌표는 메모리에 최근 3개까지만 둔다. `localStorage`, IndexedDB, 오류 로그, 분석 이벤트에 저장하지 않는다. 원본 좌표 배열이나 동선 지도도 만들지 않는다.

기기에는 별명별 누적 거리와 기념 항목 ID만 저장할 수 있다. 중단 시 마지막 좌표는 폐기한다.

서버 보상 흐름은 다음과 같다.

- 기기 누적 거리 200m마다 `walk_claim_v6()` 호출.
- 요청에는 별명·토큰·세션 ID·요청 ID만 포함.
- 좌표, 정확도, 속도, 거리, 장소 ID는 보내지 않는다.
- 최초 보상은 서버 세션 시작 150초 이후.
- 이후에도 마지막 지급에서 150초 이상 필요.
- 세션은 30분 뒤 만료.
- 하루 최대 4회, 총 XP 32·코인 16.
- 연결이 끊겨 세션이 만료되면 기기 기념은 남기되 서버 보상을 소급 지급하지 않는다.

이 방식으로 서버가 실제 200m 보행을 검증할 수는 없다. 속도 필터 역시 느린 차량·GPS 조작을 완전히 배제하지 못한다. 보상량을 작게 제한하고, GPS 전용 고가 물품·배지·확률 우대를 두지 않는다.

**성당 근접 판정**

`pet-places.ts`에 군포 용호성당의 공개 위치 한 점만 넣는다. 런타임 지도·지오코딩 API는 호출하지 않는다.

- 반경 120m.
- 정확도 30m 이하.
- `성당까지 거리 + accuracy ≤120m`를 만족하는 위치가 30초 이상 이어져야 한다.
- 최소 3개의 유효 샘플 필요.
- 통과하면 095번을 기기에만 등록한다.
- 서버에 장소 ID나 “성당 방문” 이벤트를 보내지 않는다.
- 지오펜스 접근을 위해 길을 건너거나 입장하도록 안내하지 않는다.
- 미사 출석이나 성당 실제 입장을 의미하지 않는다.

현재 저장소에는 해당 좌표가 없다. 배포 전 [수원교구 본당 안내](https://www.casuwon.or.kr/parish/parish)의 **용호 본당**과 지도 위치를 대조해 좌표를 확정해야 한다. 부산의 동명 성당 좌표를 사용하지 않는다. 좌표 검증 전에는 장소 기념만 비활성화하고 일반 GPS 거리 기능은 배포할 수 있다.

**독립 배포 가능한 5단계**

모든 단계는 기존 서비스가 작동하는 상태로 배포한다. 아래 이미지 용량은 전체 추가 자산 예상치이며 첫 화면 전송량이 아니다.

| 단계 | 변경·새 파일 | 이미지·예상 용량 | SQL | 검증 | 주요 위험 |
|---|---|---|---|---|---|
| **1. 진행 시스템 + 손맛** | `PetGame`, `PetScene`, `PetDog`, `pet.ts`, `pet-rpc`, `pet-maps`, CSS 수정. 진행·시트·identity·machine·geometry·controller 추가. v6 전체 계약 구현 | 상점 20개 아이콘·착용 레이어 약 100~180KB. 나머지 도감은 기존 자산·공통 실루엣과 텍스트 사용 | **v6 한 번**. 이후 단계의 테이블·RPC·96종 메타데이터까지 포함 | SQL 전 기존 게임, SQL 후 레벨·구매·착용·도감·업적. 중복 요청·잔액 경쟁·잠금 해제 테스트 | 기능이 많은 첫 배포. 화면 구현과 SQL 적용 순서를 분리 |
| **2. 도감 96종과 탐색 표현 완성** | `pet-catalog`, `pet-assets`, 도감·상점 시트, 탐색 결과 표현 보강 | 발견 60종·전례 12종·기념 4종 약 300~450KB. 1단계 상품 그림과 스타일 통일 | 새 SQL 없음 | 시간대별 후보, 보정, 전례 조건, 목록 지연 로드 | 생성 그림과 항목 매핑 오류 |
| **3. 스프라이트 교체** | `PetDog`, `PetScene`, `pet-sprites`, `cut_sheet` 수정. atlas packing 추가 | 강아지 14장·NPC 3장 atlas 약 0.9~1.5MB. 행동별 지연 로드 | 없음 | 프레임 기준점·의상 anchor·사진 대체·메모리 | 프레임 흔들림과 과도한 디코딩 메모리 |
| **4. 선택 GPS 산책** | `PetWalkSheet`, `pet-geolocation`, `pet-places`, 기록 관리 추가 | 2단계 기념 이미지 재사용, 추가 0KB | 없음. v6에 준비한 RPC 사용 | 권한 허용·거부·화면 잠금·차량·정지 흔들림·좌표 미전송 | 측정 오차와 보상 위조 |
| **5. 실제 폰 성능·접근성 마무리** | 자산 캐시·동작 축소·시트·CSS 조정, UI fixture·회귀 테스트 완성 | 새 필수 이미지 없음. 초과 자산 재압축 | 없음 | Android·iPhone, 느린 통신, 320px, 큰 글씨, 키보드, 뒤로 가기 | 데스크톱에서는 드러나지 않는 모바일 문제 |

1단계는 현재 사진과 SVG 표현 위에서 **레벨·코인·상점·착용·도감·업적 전체가 실제로 저장되고 동작하는 배포**다. 스프라이트가 없어도 완성된 게임 흐름이어야 한다.

1단계의 도감은 최종 96종 이름·조건을 모두 갖지만, 아직 그림이 없는 항목은 분류 실루엣을 사용한다. 이후 이미지 추가 때문에 ID나 소유 기록을 바꾸지 않는다.

각 단계는 다음 순서로 종료한다.

1. 관련 단위·화면 검증.
2. `npm run lint`, `npm run build`.
3. 해당 단계의 모바일 합격 기준 확인.
4. 기존 작업을 보존하며 `DEPLOYMENT_INDEX`를 1 증가.
5. 프로젝트 규칙대로 커밋·푸시하고 `배포 인덱스: N → M` 보고.

SQL은 Git 푸시만으로 적용된다고 가정하지 않는다. 1단계 클라이언트를 먼저 배포해 기존 RPC 대체 동작을 확인한 후 v6를 적용한다.

**DB 쓰기 없이 화면 검증**

테스트는 운영 Supabase를 사용하지 않는다.

- `PetApi`에 메모리 구현을 주입한다.
- 브라우저 시작 전에 `*.supabase.co/**` 요청을 전부 차단한다.
- mock은 서버 응답 형태와 요청 ID 재전송을 구현한다.
- fixture에는 고정 시각·고정 난수·고정 별명을 사용한다.
- 운영 빌드에는 mock 진입점을 포함하지 않는다.
- 테스트 중 외부 Supabase 요청이 한 번이라도 발생하면 실패한다.

필수 화면 fixture는 다음이다.

```text
v6 미설치
새 별명 등록
다른 토큰으로 같은 별명 접근
레벨 상승
잔액 부족 / 구매 성공 / 중복 구매
옷 착용 / 장난감 선택
새 도감 / 중복 도감 / 미발견 보정
일일 보상 한도
RPC 8초 지연 / 응답 유실 후 같은 요청 재시도
이미지 실패
행동 중 언마운트
탭 숨김 후 복귀
GPS 거부 / 위치 불량
reduced-motion
```

DB의 동시성·권한 검증은 화면 mock과 분리한다. 별도 로컬 Supabase 또는 폐기 가능한 테스트 DB에 v1~v6를 적용한다.

- anon 직접 테이블 조회·수정 거부.
- 공개 RPC 외 보조 함수 실행 거부.
- 잘못된 토큰으로 모든 개인 변경 거부.
- 동일 요청을 동시에 두 번 보내도 지급 한 번.
- 서로 다른 요청 ID로 같은 티켓 완료해도 지급 한 번.
- 마지막 잔액으로 두 상품 동시 구매 시 하나만 성공.
- 레벨 보상·배지 중복 없음.
- 시즌 외 기록 등록 거부.
- 기존 RPC 호출로 개인 재산이 늘지 않음.
- v6 적용 실패 시 기존 서비스와 데이터 유지.

**폰 성능 측정**

기준 기기는 4GB RAM급 보급형 Android Chrome과 iPhone Safari 한 대씩으로 한다. 설치 없는 일반 브라우저 탭에서 확인한다.

1. production 빌드를 사용한다.
2. 캐시 없는 최초 진입을 3회 측정한다.
3. Android는 원격 DevTools로 네트워크·Performance·Memory를 기록한다.
4. iPhone은 Safari Web Inspector로 로딩·스크롤·탭 전환을 확인한다.
5. 90초 동안 행동 8개, 맵 5개, 시트 3개를 순서대로 사용한다.
6. 게임 구역을 화면 밖으로 보낸 뒤 폴링·프레임 작업이 멈추는지 확인한다.
7. 시트를 20회 열고 닫아 메모리가 계속 증가하는지 확인한다.
8. 탭을 숨겼다 복귀하고, 느린 통신 상태에서 요청을 재시도한다.

합격 기준은 앞의 성능 예산에 더해 다음을 적용한다.

- 20회 시트 개폐 뒤 GC 후 힙 증가 5MB 이하.
- 상점·도감 스크롤 중 100ms 이상 멈춤 없음.
- 행동 종료 후 500ms 이내 입력 복구.
- RPC가 끝나지 않아도 8초 뒤 결과 확인 UI 사용 가능.
- 숨김 상태에서 게임 폴링 요청 0회.
- 네트워크 요청에 위도·경도·위치 샘플·장소 기념 ID 없음.
- 320px 폭, 글자 200% 확대에서 닫기·구매·행동 버튼 접근 가능.

**가장 위험한 3가지와 대비책**

1. **별명·GPS를 실제 신원과 보행 증명으로 오해하는 것**  
   별명은 기기 토큰으로 등록 이후의 기록만 보호한다. 기존 공동 RPC의 취약성은 남기되 개인 재산과 분리한다. GPS는 좌표를 보내지 않아 검증할 수 없으므로 하루 16코인으로 제한하고 전용 필수 콘텐츠를 두지 않는다.

2. **스프라이트 제작량과 모바일 메모리가 예상보다 커지는 것**  
   행동별 6프레임·256px로 제한하고, atlas 4개만 참조한다. 한 행동당 재생성 두 번 이후에는 기존 사진 연출을 사용한다. 진행 시스템은 그림 교체와 독립적으로 완성한다.

3. **느린 응답·중복 완료·언마운트가 잠금과 중복 지급으로 이어지는 것**  
   화면은 단일 reducer·sceneId·epoch로 관리하고, 연출 종료에 서버 지급을 연결하지 않는다. 서버는 요청 ID와 티켓 잠금으로 한 번만 처리하며, 통신 실패는 같은 요청을 재확인하도록 만든다.
