# 사용자별 도미·미네 육성과 공용 동물 출현 설계

2026-11-12. Claude와 Codex가 따로 초안을 쓰고 서로 대조해 합쳤다. 두 초안이 같았던 점, 달랐던 점과 선택 이유는 맨 끝에 있다.

## 바뀌는 것

지금은 모든 사람이 도미와 미네 두 마리를 같이 키운다. 앞으로는 이름마다 자기 도미와 미네를 가진다. 최선호로 들어오면 최선호가 키운 두 마리가, 최비호로 들어오면 최비호의 두 마리가 나온다.

지도의 동물은 반대로 모두가 같은 것을 본다. 누가 먼저 이기면 그 동물은 모두에게서 사라진다. 그래서 동물 수를 줄이고, 동물 레벨은 내 레벨이 아니라 전체 사용자의 레벨 분포에서 뽑는다.

## 사용자별로 나뉘는 것과 공유로 남는 것

| 사용자별 | 공유 |
|---|---|
| 레벨·경험치·능력치 배분·연승 | 지도 동물 출현(칸·시간대로 정해짐) |
| 직업·전직 단계·직업 기술 | 쓰러뜨린 동물 기록(누가 이기면 모두에게 사라짐) |
| 장착 기술·기술 숙련도 | 코인 줍기 선착순 |
| 지역 인증·도감(만난 동물 기록) | 같은 칸에서 겨루는 사람 표시 |
| 코인 | 순위 |
| 전투 아이템 가방 | 물품 가격·게임 규칙 |
| 꾸미기 보유·장착 | 동네 소식(누가 무엇을 했는지) |
| 배부름·기분·깨끗함·돌봄 횟수, 행동 중 잠금 | 전체 사용자 레벨 분포 |

이미 사용자별인 것(하루 제한, 탐험·산책 세션, 업적, 대결 기록)은 그대로 둔다.

## 공용 동물 출현

출현은 지금도 칸과 30분 단위 시간대로 정해져 모든 사람에게 같다. 달라지는 것은 세 가지다.

**수를 줄인다.** 칸마다 동물이 있을 확률을 30%에서 18%로 낮춘다. 동물마다 30분 시간대 안에서 15분만 머문다(시작 시각은 동물마다 다르다). 지도 전체에 동시에 있는 동물은 평균 약 43마리에서 약 13마리로 줄고, 한 시간에 새로 나오는 수는 약 85마리에서 약 51마리가 된다. 구역 대장 같은 이름 있는 동물은 시간대 내내 있다. 수치는 `lib/domine/king/spawn.ts`의 상수 두 개라서 플레이해 보고 바꾼다.

**레벨은 전체 사용자 분포에서 뽑는다.** 서버가 하루에 한 번(한국 시간 기준 그날 첫 요청) 최근 14일 안에 대결한 사용자의 도미·미네 레벨을 모아 다섯 점(최저, 25%, 50%, 75%, 최고)을 저장한다. 최저는 2를 빼고 최고는 2를 더해 폭을 넓힌다. 대상이 3마리 미만이면 경험치가 있는 모든 강아지를 쓰고, 그래도 없으면 1~5로 둔다. 상태 응답에 이 값(`levelProfile`)을 실어 보내 모든 기기가 같은 레벨을 계산한다.

**집 근처는 낮게, 먼 곳은 높게.** 구역 열 개가 분포의 서로 다른 구간을 쓴다. 성당이 있는 첫 구역은 아래쪽 절반, 가장 먼 구역은 위쪽 절반이고 사이 구역은 고르게 올라간다. 전체로는 낮은 레벨부터 높은 레벨까지 고르게 나온다. 여기에 동물마다 −3~+3의 개체 차이를 더한다.

**레벨 5 미만은 연습 기간이다.** 분포는 이미 키운 사람들 기준이라 새로 시작한 강아지가 이길 상대가 거의 없고, 동물 수까지 줄면 첫 상대를 못 찾는 일이 생긴다. 그래서 레벨 5가 되기 전까지는 지금처럼 칸의 30%에 동물이 시간대 내내 있고 레벨도 내 강아지에 맞춘다. 같은 추첨값을 쓰기 때문에 연습 기간의 동물은 다른 사람이 보는 동물을 포함하고, 누가 이기면 사라지는 것도 같다.

서버는 대결을 시작할 때 상대 레벨이 `분포 최고 + 5`와 `내 레벨 + 10` 중 큰 값 이하인지 확인한다. 경험치 상한은 지금처럼 내 레벨 + 10 기준이라 높은 레벨 동물을 이겼다고 해서 보상이 커지지 않는다. 분포 값이 없는 서버(SQL 적용 전)에서는 앱이 지금 방식으로 계산한다.

## 직업과 직업 기술

직업 다섯 개와 3단계 전직, 직업마다 기술 6개(레벨 10·15·30·40·60·80에 열림)는 전투 엔진과 서버에 이미 있다. 고르는 화면만 없었다.

직업 화면에서 직업별 능력치 변화, 직업 기술, 조건을 보여 주고 고르게 한다. 조건은 서버 규칙 그대로다. 1단계는 레벨 10과 첫 구역 대장 봉돌(E1 칸) 승리, 2단계는 레벨 30·구역 인증 3개·120코인, 3단계는 레벨 60·구역 인증 6개·300코인이다. 직업을 바꾸면 300코인이 들고 24시간에 한 번만 된다. 강아지 능력치에 맞는 직업 하나를 추천으로 표시한다.

직업 기술은 대결에서 자동으로 쓸 수 있게 한다. 직업이 있으면 기술 칸이 따로 2개 생기고, 지금 열린 직업 기술 중 가장 새로운 공격 기술 하나와 그 밖의 기술 하나가 들어간다. 원래 쓰던 기술은 줄지 않는다. 기술 목록에서는 별 표시로 구분한다.

## 서버 구조

새 스키마 `domine_pet_v22`에 사용자별 표를 만들고 기존 표는 고치지 않는다. 기존 표의 키를 바꾸려면 서로 걸린 참조를 끊어야 해서 위험하고, 그대로 두면 전환 전 상태가 백업으로 남는다.

- `wallet(player_id)`: 코인, 버전. 버전은 기존 공유 지갑 버전 + 1에서 시작한다(앱이 버전으로 최신 값을 고른다).
- `pet(player_id, pet_id)`: 배부름·기분·깨끗함·돌봄 횟수·갱신 시각, 돌봄 경험치, 행동 중 잠금(끝나는 시각·행동).
- `progress(player_id, pet_id)`: 경험치, 능력치 배분, 직업·단계·변경 시각, 장착 기술, 연승, 버전.
- `mastery`, `battle_inventory`, `certification`, `cosmetic_inventory`, `equipment`: 기존과 같은 열에 `player_id`를 키 앞에 추가.
- `encounter_record(player_id, individual_id)`: 도감과 첫 승리 판정.
- `spawn_profile(day)`: 레벨 분포.

대결 표(`battle_ticket`), 변경 이력, 요청 기록, 줍기·쓰러뜨림 기록은 이미 사용자 번호가 있거나 공유라서 그대로 쓴다. 도감 수집품(`album`)은 공유용 계정에 모여 있던 것을 계정마다 복사한다.

공개 함수 이름과 응답 모양은 바꾸지 않는다. 본문만 사용자 기준으로 다시 쓴다. 대상은 돌봄·상점·탐험 명령(`command_v6`, 약 210줄), 대결(`domine_pet_king_v17`, 약 380줄), 상태 조회와 보조 함수, 가입(가입할 때 지갑과 두 마리를 만든다)이다.

같이 고치는 부하 문제는 네 가지다. 전 사용자가 공유 지갑 한 줄을 잠그고 줄 서던 것이 사용자별 잠금으로 바뀐다. 상태 조회가 매번 돌봄 기록 전체를 세어 만들던 "오늘 순위"는 화면에서 쓰지 않으므로 빈 값으로 돌려준다. 상태 조회에서 잠금과 쓰기를 없앤다. 다른 사람의 만료된 대결까지 매번 정리하던 것을 내 것만 정리하게 한다.

이름만으로 다른 사람 강아지에 밥을 줄 수 있는 옛 함수(`domine_pet_care_for`, `domine_pet_care`)는 바깥에서 부르지 못하게 권한을 뺀다. 옛 상태 조회는 읽기 전용으로 남긴다.

## 기존 데이터

지금의 공유 상태(레벨, 코인, 아이템, 꾸미기, 돌봄 수치, 인증, 도감)를 기존 계정 모두에게 똑같이 복사한다. 모두가 같이 키운 결과이기 때문이다. 코인과 아이템 총량이 계정 수만큼 늘어나는 것은 받아들인다. 새 계정은 레벨 1, 코인 0에서 시작한다.

전환은 한 트랜잭션이다. 진행 중인 대결은 취소하고 맡긴 아이템을 돌려준 다음 복사하고, 함수를 바꾸고, 앱이 기기 캐시를 비우도록 초기화 표식(`reset_epoch`)을 올린다. 실패하면 전부 되돌아간다. 전환 뒤에 문제가 생기면 이전 함수 본문을 다시 설치하는 되돌리기 SQL을 실행한다. 기존 표를 건드리지 않았으므로 전환 직전 상태로 돌아간다. 다만 전환 뒤에 각자 키운 것은 되돌리면 사라진다.

## 검증과 적용 순서

마이그레이션 파일 전체를 메모리 Postgres(PGlite)에서 실제로 실행하는 테스트를 추가했다. 지금까지는 SQL을 글자로만 검사해서 실행 오류를 운영 서버에서 처음 만났다.

테스트로 확인할 것: 두 계정의 성장·코인·아이템·돌봄·꾸미기·인증·직업이 서로 섞이지 않는다. 쓰러뜨린 동물과 줍기는 공유된다. 같은 요청을 다시 보내도 한 번만 반영된다. 전환 전 공유 상태와 전환 후 각 계정 상태가 같다. 상태 조회는 아무것도 쓰지 않는다. 경험치·코인 규칙은 그대로다. 되돌리기 SQL 뒤에 예전 응답이 나온다. 이 테스트는 연결 하나로 돌기 때문에 두 사람이 동시에 요청할 때의 잠금 경합은 확인하지 못한다.

적용은 두 번에 나눈다. 먼저 레벨 분포(v22)를 적용한다. 작은 변경이고 앱은 적용 전후 모두 동작한다. 그다음 사용자별 전환(v23)을 적용한다. 적용 전에 계정·행 수를 세고, 적용 뒤에 두 계정의 상태를 읽어 확인한다.

## 이번에 하지 않는 것

이름만 알면 그 계정으로 들어갈 수 있는 것은 그대로다. 지금까지는 공유 강아지라 문제가 작았지만 개인 강아지가 되면 남이 내 이름으로 들어와 코인을 쓰거나 직업을 바꿀 수 있다. 비밀번호를 붙이는 방법은 두 가지가 나왔다. 이름과 4자리 번호를 합쳐 비밀값을 만드는 간단한 방식과, 느린 해시와 로그인 세션을 두는 방식이다. 어느 쪽이든 먼저 비밀번호를 거는 사람이 그 이름을 차지하는 문제가 남고, 시도 횟수 제한이 필요하다(지금 서버의 횟수 제한 함수는 항상 통과시킨다). 사용자별 전환이 안정된 뒤 따로 정한다.

능력치 직접 배분 화면, 기술 장착 화면, 순위 화면, 협동 레이드도 이번 범위가 아니다.

## 두 초안의 대조

같았던 점: 범위는 전부 사용자별, 새 스키마에 표를 만들고 기존 표는 두기, 기존 계정에 공유 상태 복사, 공개 함수 이름과 응답 유지, 상태 조회에서 쓰기 제거.

달랐던 점과 선택:

- 쓰러뜨린 동물과 줍기. Codex는 사용자별, Claude도 처음에는 사용자별을 제안했다. 소유자가 공유로 정했다(먼저 잡는 사람이 임자).
- 대결 표. Codex는 새 표로 옮기자고 했고 Claude는 기존 표 재사용을 골랐다. 이미 사용자 번호가 있고 옮길 이유가 없어서 재사용한다.
- 이력. Codex는 개인 이력과 인증된 조회 함수를 제안했다. 동물을 두고 경쟁하게 되면 "누가 무엇을 잡았는지"가 보이는 편이 낫고 서버 변경도 없어서 공유 그대로 둔다.
- 전환 방식. Claude는 조각으로 나눠 일부 계정만 먼저 켜는 방식을, Codex는 한 트랜잭션을 제안했다. 메모리 Postgres로 전체를 미리 실행할 수 있게 되어 한 트랜잭션과 되돌리기 SQL로 한다. 함수 본문을 두 벌 유지하지 않아도 된다.
- 백업. Codex는 `pg_dump`를 권했다. 접속 비밀번호가 필요해 소유자만 할 수 있다. 이번 전환은 기존 표를 고치지 않으므로 기존 표 자체가 전환 전 상태로 남는다.
- 인증. Codex가 짚은 두 가지를 반영했다. 서버에 저장된 값은 앱이 보낸 비밀값을 한 번 더 해시한 것이고, 횟수 제한 함수는 지금 항상 통과시킨다.
